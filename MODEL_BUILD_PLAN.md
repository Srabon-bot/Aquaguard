## Part 1 — Data Collection

**Free-tools-only stack (confirmed 2026-08-02) — read this before touching any checkbox below:**

Since real historical BWDB/FFWC gauge readings are a paid product (see 1a), the "gauge" role in this
project is filled instead by **NASA GFMS** (below) — a free, no-registration, 25-year continuous
satellite/model dataset that already includes a locally-calibrated flood-intensity signal and a
streamflow (discharge) signal per grid cell. Concretely: instead of training on real station history at
Bahadurabad/Sirajganj/etc., we train on the GFMS grid cell(s) co-located with those station coordinates
— a "virtual gauge." This is a standard technique in this field (it's literally what GFMS itself is *for* —
global flood monitoring in basins without open gauge networks) and it means **the entire core pipeline
(Parts 1–4) needs zero registrations, zero payment, and zero waiting on any external approval.**

Final free-tools source map (updated 2026-08-02, second pass — see below):
| Role | Source | Registration? | Coverage |
|---|---|---|---|
| Rainfall (feature, training + **live inference**) | CHIRPS (bulk historical) + **Open-Meteo Forecast API** (live, already wired) | None | CHIRPS 1981–present; Open-Meteo live+forecast |
| River discharge (feature+label basis, training + **live inference**) | **Open-Meteo Flood API** (GloFAS v4 reanalysis+forecast, new primary — see below) | None | ~1998–present + 7-day forecast, same JSON endpoint for both historical bulk queries and live |
| Flood-intensity label refinement (optional) | NASA GFMS raw grids | None | 2001–~2026-02 only — **live feed confirmed stalled since 2026-02-02, historical archive still solid through then** |
| Event-level validation (optional) | MODIS Global Flood Database (Google Earth Engine) | Free signup | 2000–2018, 913 events |
| Event-level validation (optional) | Dartmouth Flood Observatory | None (site structure changed, re-check when used) | 1985–present |
| Live current-level enrichment (inference-time only, not training) | FFWC API / BWDB Hydrology login | Free (already have BWDB login) | real-time only |

**2026-08-02 second pass — simpler discharge source found:** `flood-api.open-meteo.com` (same provider as the rainfall API already wired into `app/services/weather.py`) serves GloFAS v4 river discharge as plain JSON — free, no API key for non-commercial use, no rate limit documented — via a single endpoint that takes `start_date`/`end_date` (verified working back to at least 1998, e.g. the '98 mega-flood; null before ~1990s) **and** `past_days`/`forecast_days` for live current + 7-day-ahead forecast. This does two things:
1. **Simplifies Part 1c**: instead of downloading/parsing raw GFMS binary grids (custom row/col math, unverified grid orientation, resumable multi-year 3-hourly file loop), we can pull the same discharge history as tidy JSON per virtual-station coordinate — far less engineering. GFMS is demoted to optional (still useful later if we want its pre-calibrated flood-intensity threshold as an extra label signal, but not required to get a working pipeline).
2. **Directly answers the live-internet-access ask below** — the exact same API call (just with `past_days`/`forecast_days` instead of a historical date range) gives current + forecast discharge at inference time, with zero new registration, mirroring the pattern `fetch_rainfall()` already uses for rainfall.

**Important negative finding on GFMS**: while researching this, discovered that `eagle2.umd.edu`'s GFMS archive — which looked "live" (year folders exist through 2026) — actually **stopped receiving new data on 2026-02-02** (confirmed precisely: `2026/202601/` has ~246 real files, `2026/202602/` cuts off after `Flood_byStor_2026020209.bin`, and every month from `202603` onward only contains a broken wildcard placeholder entry, not real files). So GFMS is fine as a **historical** archive (2001 through early Feb 2026) but must **not** be relied on as a live/current-conditions feed — it's effectively a dead/stalled real-time pipeline right now, similar to the earlier FFWC/BWDB findings in this project. Use Open-Meteo for anything live.

## Part 3 — Feature Engineering

**Model-research note (2026-08-07)**, from searching recent (2024-2025) published Bangladesh-specific flood-ML work before starting this part, not generic flood-ML literature: gradient-boosted trees are empirically the strongest performer in this exact domain (one comparative study: Gradient Boosting hit 95.4% accuracy vs. logistic regression/plain RF) — **validates the existing plan below, no model-family change needed.** Commonly-cited top features across that literature: precipitation, distance from river, elevation, land use, **soil type/moisture** — rainfall and (as of today) soil moisture are covered; elevation/land-use are lower priority (they matter more for spatial risk mapping across districts than for a single station's time-series risk, which is this project's core loop). SHAP-based per-prediction explainability is what current published work uses for interpretability — noted for Part 4/5, see below.

- [ ] Lagged discharge/storage/flood-intensity (t-1..t-5) per virtual station, from GFMS + Open-Meteo discharge
- [ ] Rolling rainfall sums (7d/14d, local + upstream) and trend ratios, from Open-Meteo historical rainfall
- [ ] **Soil moisture as a feature (new, added 2026-08-07)** — `soil_moisture_local` (0-7cm, m³/m³) directly, plus probably a rolling trend/anomaly version (e.g. vs. a seasonal baseline) since absolute soil moisture varies a lot by season and what likely matters more is "wetter than usual for this time of year." Deliberately kept at the same depth/units the live Open-Meteo estimate and the eventual IoT probe (Part 5b) will report, so training and live-serving stay consistent.
- [ ] Upstream travel-time lag features (e.g. Bahadurabad → downstream Sirajganj shifted by travel time)
- [ ] Label: GFMS `Flood_byStor` (flood intensity above threshold) becomes positive within 24h / 48h / 72h horizons — this directly replaces the original "exceeds `danger_level_m`" label design, since we no longer have real danger-level gauge readings. **Label source decided 2026-08-07** (GFMS primary, see cross-validation entry below) after checking it against both MCDWD satellite observation and real discharge data.

### Part 5b — Full end-to-end system architecture + IoT soil moisture sensor (added 2026-08-07, per user's scenario)

User described the target end-state system (paraphrased): a website connected to their pond-monitoring
IoT device, showing (1) live sensor data from the device, (2) a live weather section for the farmer's
location pulled from the internet, and (3) a manual "check flood risk in the next 2-3 days" button. That
button's request goes to a **"middle system"** which, based on the location, gathers the live + recent
data the model needs from the internet, packages it, feeds the trained model, and returns the answer to
the site.

**This is already the shape of what's built** — `app/main.py`'s `/predict/risk` endpoint *is* that middle
system (location in, live-data-fetch + model.predict() + plain-language reasoning out). No architectural
change needed, just filling in gaps as the model/data work above lands:

- [x] **Live rainfall** — done, see Part 5a.
- [ ] **Live river discharge** — planned, see Part 5a (not yet implemented).
- [ ] **Live soil moisture (new)** — add alongside `fetch_rainfall()`: same Open-Meteo Forecast API,
  `daily=soil_moisture_0_to_7cm_mean` (verified working live 2026-08-07: returns real current+forecast
  values, e.g. 0.483-0.509 m³/m³ for Bahadurabad this week). Deliberately the **same depth (0-7cm) and
  units (m³/m³)** as both the ERA5-Land historical training feature (Part 1b/3) and the eventual IoT
  probe below — keeping one consistent feature definition end-to-end is more important than picking a
  "better" depth in isolation, since a mismatch would silently feed the model an apples-to-oranges number.
- [ ] **IoT soil moisture sensor, once the device exists (new)** — the user's own pond-monitoring device
  will report live local soil moisture. Design intent (not yet implementable — no device/protocol details
  yet, this is groundwork for later, not a blocker to Part 3/4): the middle system's soil-moisture feature
  should prefer a fresh reading pushed/pulled from the user's own device over the Open-Meteo estimate
  above, since it's real ground-truth at the exact farm location rather than a ~9km reanalysis grid cell.
  Fallback chain: **IoT sensor reading (if connected & fresh) → Open-Meteo live forecast estimate (always
  available) → this is the same 3-tier pattern already used for station water level in `ffwc.py`.** When
  wiring the real device, the ingestion endpoint/format needs to normalize whatever the sensor natively
  reports (often a raw resistance/capacitance/percentage reading) into volumetric water content (m³/m³) at
  a comparable depth — a naive unit mismatch here would corrupt this feature silently, worth double-
  checking against a known-wet/known-dry calibration reading rather than trusting the sensor datasheet
  alone.
- [ ] **Live weather section on the site (not the model, a UI display concern)** — the user wants a plain
  "today's weather here" panel on the website, separate from the flood-risk button. This can reuse
  `fetch_rainfall()`'s same Open-Meteo call (or a small superset of it — temperature/humidity are free on
  the same endpoint) rather than needing a second integration; worth a small dedicated `/weather/current`
  endpoint on the same backend rather than making the frontend call Open-Meteo directly, so there's one
  place that owns "how we talk to Open-Meteo" (caching, error handling, consistent units) for the whole
  site, not two.

**Not started yet** — this is documentation/design for Part 5, which comes after Parts 3-4 (feature
engineering, model training) in the build order. Captured here now so the shape of the end system is on
record and Part 3's feature choices (e.g. using soil moisture at all) are made with the live-serving path
in mind, not just what's convenient for historical training.

### 2026-08-14 (built the real 3-model pipeline: cascade feature, then one combined alert output)

Key finding: the discharge-forecaster-feeds-classifier idea flagged back when model #2 was first built (but never implemented) has a name in the literature -- "cascade generalization" -- and stacking a learned meta-model was confirmed (again) to be risky at this project's data scale, reinforcing the existing preference for transparent formulas over black-box combiners. Proposed architecture: (1) cascade the discharge forecast into the classifier as a live feature, (2) keep the existing classifier x susceptibility decision-level combination, (3) discretize the result into a named alert level (GloFAS-style) instead of a bare percentage.
